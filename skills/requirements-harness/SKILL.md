# 要件定義ハーネス

やりたいことを仕様に落とすには、**何を決めないといけないのかの全体像**と、
**決定どうしの依存関係**が要る。エクセルやQA表ではどちらも表現できない。
この仕組みは、その2つを機械可読なファイルで持ち、**決定論的な検査で観点を生む**。

## 役割分担 — ここを崩さない

| | 担当 | 理由 |
|---|---|---|
| **言われたこと**を論点にする | `reqmap-extractor`（引用を機械が照合） | モデルの自己申告には頼らない |
| **言われなかったこと**を観点にする | `reqmap` のチェッカ（決定論・LLM不使用） | 幻覚まじりの観点リストは一度で信用を失う |
| 観点を**日本語にする** | あなた（Claude） | 機械の出力は相手に出せる文になっていない |
| 観点に**答える** | 人 | |
| 決定を**書く** | 人（またはあなたが人の合意を書き取る） | 機械が決定欄に触った瞬間、この仕組みは信用できなくなる |

`reqmap recalc` が書くのは計算済みの7キーだけ。
`status` `decision` `severity` には**絶対に触らない**。あなたも同じ。

## コマンド

```bash
R=${CLAUDE_PLUGIN_ROOT}/scripts/reqmap-cli
$R status --root=<dir>    # 静かな点検。人が動くものだけ。まずこれ
$R gaps   --root=<dir>    # 確認観点。何も書かない
$R recalc --root=<dir>    # 影響度・逆算日付を frontmatter に書く
$R view   --root=<dir>    # HTML を .reqmap/index.html に出す
$R json   --root=<dir>    # 全データを JSON で（他ツール連携用）
$R init   <dir>           # 雛形を作る
$R review --root=<dir>    # Change Set を点検する（引用照合。何も書かない）
$R apply  --root=<dir>    # Change Set の auto を適用する
$R doctor --root=<dir>    # この vault をちゃんと読めているかを点検する
$R changes --root=<dir>   # 前回見たときから書き換わった決定
$R gaps --new --root=<dir>      # 前回見たときから新しく出た観点だけ
$R gaps --snapshot --root=<dir> # 「ここまでは見た」を記録する
```

## ID は slug

`data.retention-period` のような形。ファイル名と一致させます。連番は使いません。

ID が要るのは**タイトルが変わっても参照が壊れないため**の一点だけで、
連番である必要はありません。むしろ連番には4つの問題があります:
採番の調整が要る／意味を持たない／分割すると親子が読めない／若い番号が重要と誤読される。

slug には副作用として良い性質があります。**slug が付けられない論点は、論点が同居している。**
「保持期間・受付経路・対象範囲」に1つの slug は付きません。分割の合図として使えます。

相手側の番号（QA表の #12 など）は `ledger:` に別で持ちます。**ID には混ぜない。**
リネームしたくなったら `aliases:` に旧IDを残せば `[[リンク]]` は壊れません。

## 進め方

### 0. 議事録があるなら、まず取り込む
`reqmap-extractor` サブエージェントに投げます（`/reqmap-extract`）。
**あなたが questions/ に直接書かないこと。** Change Set を経由します。

議事録から論点を起こすのはモデルの仕事ですが、モデルが直接書くと
**何が人の言葉で何がモデルの創作かの区別が消えます。** 一度混ざったら分離できません。
Change Set は1件ごとに原文からの逐語引用を持ち、**機械が原文と照合します。**
原文に無い引用は blocked になり、決して適用されません。

`review` → `blocked` があれば原文を確認 → `human` を1件ずつ確認 → `apply` の順。

### 0.2 毎回まずここ
`changes` → 決定が書き換わっていないか。`status` → 動くものがあるか。
どちらも何も書きません。

### 0.5 立ち上げ直後とスキーマを触ったあとは doctor
`doctor` は観点を出さず、**この vault をちゃんと読めているか**だけを見ます。
読めていないものを黙って捨てると、点検が不完全なまま「異常なし」に見えます。

特に効くのが**グリッドの語が効いているか**の点検です。
「その領域に論点がそれなりにあるのに、行の語が1件も当たらない」なら、語が実体と
合っていないか、その観点が領域をまたいでいます。語が効いていないと、
**既にある論点を「真の空白」として出してしまいます。**

領域を横断する観点（国モデル差分・異常系など）のグリッドは `area:` を指定しないこと。
指定すると他領域の既存論点が候補から外れます。

### 1. 状況を掴む
`status` → `gaps`。**先に論点を起票しない。**
グリッドと FSL が先で、論点は観点から生まれる。逆をやると資料に書いてあることの
書き写しになり、「資料に書かれていないこと」が永久に出てこない。

### 2. 観点を人に出せる質問に変える
`gaps` の `question` は機械が組んだ文なので、そのまま相手に出さない。
**1メッセージにつき3件まで。** 100件出すツールは使われなくなる。
`次に決める順` の上位から採り、こう組み立てる:

> いま決まっていないこと → それが決まらないと何が止まるか → 選択肢 → いつまでに欲しいか

### 3. 答えが返ったら論点ページに書く
`questions/<領域>/<ID> <短い名前>.md` を新規作成、または既存を更新する。

- **1ページ1論点。** 「保持期間・受付経路・対象範囲」のように3つ入っていたら分割する。
  影響度が高いのに3つまとめて止まる、が最悪。slug が付けられないのが合図。
- 依存は本文の `## 前提` に `[[リンク]]` で書く。**この見出しの外に書くと数えられない。**
- 前提が3本以上なら、たぶん論点が同居している。
- グリッドのマスを埋めたら frontmatter の `cells:` に `<grid>:<row> x <col>` を足す。
  ページは増やさず、結合だけ持つ。
- 決まったら `status: decided` にして `## 決まったこと` に結論と根拠を書く。
  **根拠のない決定は書かない。**

### 3.5 やりとりを log に残す

質問を出した日・返ってきた日を frontmatter の `log:` に積みます。**追記だけ。**

```yaml
log:
  - 2026-09-10 asked | 定例で確認依頼
  - 2026-09-24 answered | 保持期間は5年と回答
  - 2026-09-24 decided
```

これを書くと3つ変わります。

- **回答日数が仮置きから実測になる。** `ask_by` の逆算精度が上がります
- **催促どきが出る**（`turn.no_response`）。出した記録はあるのに誰も数えていない、
  が一番よくある取りこぼしです
- **聞き直しの回数と、決定がひっくり返った回数が出る。**
  3回聞き直しているなら相手の問題ではなく**問いの立て方の問題**、
  2回ひっくり返った決定は3回目もひっくり返ります

本文に「⚠ 前提を差し替えた（2026-09-13）」と散文で書いても機械は読めません。
**型を付けて初めて数えられます。**

### 4. 書いたら recalc → status
影響度と日付が変わる。`recalc --check` で規約違反が出たら先に直す。

## 判断に迷ったときの原則

**出しすぎない。** 「今週決めないと止まる3件」のほうが、正しい100件より価値がある。
毎朝同じ40件を見せると読まれなくなるので、`gaps --new` で**前回から増えた分**だけを出す。
findings のIDは内容から決まるので、1件増えても他のIDはずれない。

**すでに出して返事待ちのものを「いま聞け」と言わない。** `status` は log を見て除外する。
出した記録があるのに再提案されると、一覧そのものが信用されなくなる。

**推測しない。** グリッドの候補マッチは推定なので、`cells:` を機械に書かせない。
人に確認してから書く。

**「依存が無い」を信じない。** 前提も下流も空の論点は、独立している証拠ではなく、
辺の書き忘れの可能性が同じだけある。書き忘れていた場合、影響度も期限も**過小評価**されて
順位表の下に沈む。`graph.isolated` が出たら必ず確認する。

**仮置きには必ず期限を付ける。** `expires` の無い仮置きは誰も見直さない。
期限切れの仮置きは、いちばん高い確率で炎上する。

**skip には理由を書く。** 理由のない skip は、検討したのか忘れたのか区別がつかない。
skip は件数を減らす欄ではなく、検討した証跡を残す欄。

## ファイルの置き場所

```
<project>/
  reqmap.yml           設定（マイルストーン・領域・回答日数）
  questions/           1論点1ファイル。Obsidian でそのまま開ける
  models/grids/*.yml   N×M の網羅グリッド → 観点の供給源
  models/fsm/*.fsl     状態遷移（jssm互換）→ 状態×イベントの網羅
  .reqmap/             出力（HTML・JSON）。生成物なので手で触らない
```

Obsidian は**任意**。`## 前提` の wikilink がそのままグラフビューの辺になるので
使えば便利だが、CLI と HTML は Obsidian 無しで完結する。

## 設計フェーズへ渡すとき

**設計ハーネスは作りません。** 設計は各メンバーがそれぞれAIエージェントと進める前提です。

設計側に `derives_from` のような記帳を求めるのは定着しません。
**書くのは設計する人で、得をするのは後から変更を追う人**だからです。
書く人に見返りが無いものは書かれません。

代わりに、要件側だけで完結させます。

```bash
$R changes --root=<dir>          # 前回見たときから書き換わった決定
$R gaps --snapshot --root=<dir>  # 見終わったら基準を進める
```

分散して設計しているとき本当に困るのは「どの設計書が古いか」ではなく、
**決定が変わったことに誰も気づかない**ことです。先週見た決定が今週書き換わっていても、
本人は知らないまま設計を進めます。`changes` を見れば、自分の設計に効くかは自分で判断できます。

指紋は `status` と「決まったこと」の本文から取るので、
**決定日をそのままに結論だけ直した場合も出ます。**

`.reqmap/` は**各自のもの**です（`init` が `.gitignore` を置きます）。
「前回自分が見たとき」の基準が入るので、コミットすると他人の基準で上書きされます。

`decided` にするときは `## 決まったこと` に結論と根拠を必ず書くこと。
空のまま decided にすると `rule.decided_without_rationale` が出ます。
**根拠のない決定は3か月後に必ず蒸し返されます。**
