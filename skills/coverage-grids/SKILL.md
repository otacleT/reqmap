# 網羅グリッドと FSL

**観点の質はここで決まる。** チェッカを増やすことではなく、グリッドを正しく引くことが本体。

## なぜグリッドが要るか

資料どうしを突き合わせる方式では、「資料に書いてあることの取りこぼし」しか拾えない。
**「資料にそもそも書かれていないこと」は構造的に出てこない。**

実案件でよく見る形:
> 「保持期間の年数がどこにも存在しない」「ログの保持期間・保存先は未定義」
> 「削除仕様がドキュメント上まったく存在しない」

グリッドは「**あるべきマス**」を人が宣言し、機械が「埋まっていないマス」を引く。
資料に無くても穴が出るのはこのため。**観点を新しく生む唯一の経路。**

## 書式

```yaml
id: lifecycle
title: データのライフサイクル
area: A-02                      # 候補マッチをこの領域に限定する

rows:
  - user | アカウント・ユーザー情報 | アカウント,会員,退会
cols:
  - retain | 保持期間 | 保持期間,有効期限,保存期間
skip:
  - user x retain | 全社規程で5年と確定済み（2026-09-01 情シス）
```

第3フィールドは**題名に出る語**。これで既存の論点と突き合わせる。

**語は人が書く。機械に分かち書きをさせない。** 書かなければ候補は出ず、そのマスは
「真の空白」に落ちる。**安全側に倒すのは意図**で、見落としより余分な確認のほうが安い。

## 3段階の出し分け（出しすぎ対策）

| | 意味 | 出し方 |
|---|---|---|
| 真の空白 | 候補の論点すら無い | **全部出す。これが新しい観点** |
| 候補あり | 題名の近い論点がある | 件数だけ。`cells:` を書けば消える |
| 紐付け済み | `cells:` が書いてある | 件数だけ |

さらに2段の畳み込みが入る。**これが無いと使われなくなる**:

- **行が丸ごと空** → 1件にまとめる。その行はまだ誰も触っていないので、
  マスごとに聞くより「この種別の扱いを一度決める」ほうが早い
- **グリッドが丸ごと空** → 1件にまとめる。これは「マスが無い」ではなく
  **領域がまだ方針レベルで、マス単位に落ちていない**という別種の指摘

## skip の扱い

**理由のない skip は書かない。** 消せば観点として復活する。
skip は件数を減らす欄ではなく、**検討した証跡を残す欄**。

グリッドごと消すのも避ける。たとえば多言語展開の予定が無い案件でも、
グリッドを消さずに「単一地域のみ・2026年時点」と理由を書いて残すほうが、
後から方針が変わったときに気づける。

## FSL（状態遷移）

```
machine_name: 注文ステータス;

// @area: A-04
// @events: submit, pay, timeout, cancel, refund
// @terminal: delivered, cancelled
// @impossible: draft x pay      // 未送信の注文に決済は発生しない
// @depends_on: Q-001

draft            'submit' -> pending_payment;
pending_payment  'pay'    -> paid;
```

**全体を形式化しない。** 網羅性が定義できる部分だけ。
効くのは状態遷移・権限・データライフサイクルの3つ。

状態×イベントは**全マス総当たりにしない**（チェッカ側で対処済み）。
総当たりは `draft × deliver`（未送信の注文を受け渡す）のような無意味セルで埋まる。
実測で 31件 → 10件 になり、残った10件は全部意味のある質問だった:

| セル | 実際に聞いていること |
|---|---|
| `pending_payment × submit` | **二重送信**したらどうなる？ |
| `paid × pay` | **二重決済**は防げている？ |
| `paid × cancel` | 決済後・処理前のキャンセルは返金あり？ |
| `refund`（未使用） | 返金はどの状態から発生する？ |

「そのイベントが定義済みの状態の**隣**」だけを問い、遠いセルは件数のみ記録する。
`@impossible` は抑制ではなく**判断の記録**なので、必ずコメントで理由を書く。

## 語彙を案件から持ち出さない — **実際に起きた失敗**

同じセッションで複数の案件を扱うと、**直前に読んだ案件の語彙が次の案件に漏れます。**

このハーネス自身がその失敗をやりました。実案件（肌解析アプリ）を分析した直後に
架空のサンプル（テイクアウト注文アプリ）を作ったところ、サンプルの論点に
**「診断データの保持期間」**という、注文アプリにはあり得ない語が紛れ込みました。
結果、サンプルを見た人が「なぜ自分の案件に注文と決済の話が入っているのか」と混乱しました。

守ること:

- **グリッドの行を引くときは、その案件の資料に実際に出てくる語だけを使う。**
  「たぶんこう呼ぶだろう」で書かない。資料を開いて、書かれている語を写す
- **論点のタイトルも同じ。** 自分が直前に別案件で使った言い回しを流用しない
- 議事録からの抽出は `quote` の原文照合が守ってくれるが、**グリッドの行には
  その守りが無い。** ここだけは人が見るしかない
- 迷ったら `reqmap doctor` を実行する。「論点があるのに語が1件も当たらない行」は、
  語が案件の実体と合っていない合図

## 観点が出すぎる／出なさすぎるとき

| 症状 | 直すところ |
|---|---|
| 無意味なマスが多い | 行・列の粒度が細かすぎる。統合する |
| 既存の論点と重複する | 第3フィールドの語が足りない。題名に出る語を足す |
| 何も出ない | 行・列が案件の実体と合っていない。設計ドキュメントから引き直す |
| 全部 high で読めない | `reqmap.yml` の `areas` のリスクを見直す。全部 high は無意味 |

グリッドの行・列は**実データ構造と一致させる**。
例: 問診回答が診断データに含まれるなら、独立行にせず診断データの行に畳む。
