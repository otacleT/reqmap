# 網羅グリッドと FSL

**観点の質はここで決まる。** チェッカを増やすことではなく、グリッドを正しく引くことが本体。

## なぜグリッドが要るか

資料どうしを突き合わせる方式では、「資料に書いてあることの取りこぼし」しか拾えない。
**「資料にそもそも書かれていないこと」は構造的に出てこない。**

実案件でよく見る形:
> 「保持期間の年数がどこにも存在しない」「ログの保持期間・保存先は未定義」
> 「削除仕様がドキュメント上まったく存在しない」

グリッドは「**あるべきマス**」を人が宣言し、機械が「埋まっていないマス」を引く。
資料に無くても穴が出るのはこのため。**観点を新しく生む唯一の経路。**

## 書式

```yaml
id: lifecycle
title: データのライフサイクル
area: A-02                      # 候補マッチをこの領域に限定する

rows:
  - user | アカウント・ユーザー情報 | アカウント,会員,退会
cols:
  - retain | 保持期間 | 保持期間,有効期限,保存期間
skip:
  - user x retain | 全社規程で5年と確定済み（2026-09-01 情シス）
```

第3フィールドは**題名に出る語**。これで既存の論点と突き合わせる。

**語は人が書く。機械に分かち書きをさせない。** 書かなければ候補は出ず、そのマスは
「真の空白」に落ちる。**安全側に倒すのは意図**で、見落としより余分な確認のほうが安い。

## 3段階の出し分け（出しすぎ対策）

| | 意味 | 出し方 |
|---|---|---|
| 真の空白 | 候補の論点すら無い | **全部出す。これが新しい観点** |
| 候補あり | 題名の近い論点がある | 件数だけ。`cells:` を書けば消える |
| 紐付け済み | `cells:` が書いてある | 件数だけ |

さらに2段の畳み込みが入る。**これが無いと使われなくなる**:

- **行が丸ごと空** → 1件にまとめる。その行はまだ誰も触っていないので、
  マスごとに聞くより「この種別の扱いを一度決める」ほうが早い
- **グリッドが丸ごと空** → 1件にまとめる。これは「マスが無い」ではなく
  **領域がまだ方針レベルで、マス単位に落ちていない**という別種の指摘

## skip の扱い

**理由のない skip は書かない。** 消せば観点として復活する。
skip は件数を減らす欄ではなく、**検討した証跡を残す欄**。

グリッドごと消すのも避ける。たとえば多言語展開の予定が無い案件でも、
グリッドを消さずに「単一地域のみ・2026年時点」と理由を書いて残すほうが、
後から方針が変わったときに気づける。

## FSL（状態遷移）

FSL は [fslc](https://github.com/ymm-oss/fsl) の `requirements` 方言。**reqmap が問い、fslc が検証する。**
仕様そのものの書き方は fslc 同梱の `fsl-requirements` スキルに任せ、ここでは reqmap 側の
指令と、観点の出方だけを扱う。

```fsl
// @area: A-04
// @depends_on: Q-006
// @events: refund            // まだ遷移が無いイベントも網羅の対象にする
// @critical: cancel          // 隣接に限らず全状態で問う
// @impossible: Draft x pay   // 未送信の注文に決済は発生しない（未検証の記録）

requirements OrderStatus {
  process Order {
    stages Draft, PendingPayment, Paid, Cancelled
    initial Draft
    transition submit Draft          -> PendingPayment by Customer covers REQ-ORDER-001 "注文を送信する"
    transition pay    PendingPayment -> Paid           by Customer covers REQ-ORDER-002 "支払いで確定する"
    @reqmap.event("cancel")                            // 表の上では cancel と同じイベント
    @undecided("Q-006 支払後の返金条件は決定待ち")      // 先頭は論点ID
    transition cancel_paid Paid      -> Cancelled      by Customer covers REQ-ORDER-009 "支払後のキャンセル"
  }
  forbidden FB-ORDER-002 "支払済み注文への再決済は拒否される" {   // 「拒否する」と決めたマスは forbidden に
    submit(0) pay(0) pay(0)
    expect rejected
  }
  terminal { forall c: Order { stage(c) == Paid or stage(c) == Cancelled } }
}
verify { instances Order = 2 }
```

**全体を形式化しない。** 網羅性が定義できる部分だけ。効くのは状態遷移・権限・データライフサイクルの3つ。

### 観点の出方

| check | 出どころ | 何を聞いているか |
|---|---|---|
| `fsl.state_event_hole` | reqmap（表） | `Paid × pay` 二重決済は？ `Preparing × cancel` 調理中のキャンセルは？ |
| `fsl.unused_event` | reqmap（表） | `refund` はどの状態から発生する？ |
| `fsl.forbidden_accepted` | fslc | 後から足した遷移が、前に書いた禁止経路を破っている（決定どうしの矛盾） |
| `fsl.dead_end` / `fsl.dead_action` / `fsl.unreachable_stage` | fslc | 行き止まり／起きない遷移／到達しない状態 |
| `fsl.stale_undecided` / `fsl.undecided_unlinked` | reqmap（注釈） | 論点は決まったのに仕様が古い／未決定なのに起票されていない |
| `fsl.spec_behind_decision` | reqmap（log と更新日） | 紐付いた論点の決定日より仕様が古い（写し忘れ） |
| `fsl.thin_spec` | reqmap | forbidden も acceptance も無く、決定を写しても矛盾が出ない |

状態×イベントは**全マス総当たりにしない**。総当たりは `Draft × deliver`（未送信の注文を受け渡す）
のような無意味セルで埋まる。「そのイベントが定義済みの状態の**隣**」だけを問い、遠いセルは件数のみ記録する。

ただし隣接だけだと `Preparing × cancel`（調理中のキャンセル）のような**一番揉めるマスが抑制側に落ちる**。
キャンセル・返金のように状態を問わず揉めるイベントは `@critical` に書き、全状態で問わせる。

### マスへの答え方

| 答え | 書き方 | 検証 |
|---|---|---|
| こう遷移する | `transition` を足す | される |
| 拒否する | `forbidden` に操作列を書く | される。後から破られれば `fsl.forbidden_accepted` |
| 起こり得ない | `// @impossible: State x event | 理由` | されない。**判断の記録**として理由を必ず書く |
| まだ決められない | `@undecided("Q-xxx 理由")` を遷移の前に | 論点が決まったのに残っていれば `fsl.stale_undecided` |
| 相手に聞く | `reqmap gaps --file <観点ID>` で論点に | 起票済み（cells: で紐付け）として表から消える |

`forbidden` の最終ステップが当たるマスは「回答済み」として表から消える。`@impossible` も同じだが、
こちらは検証されないので、後から仕様が変わっても気づけない。迷ったら `forbidden`。

同じイベントを複数の遷移に分けたとき（`cancel` と `cancel_paid`）は、遷移の前に
`@reqmap.event("cancel")` を書く。書かないと `cancel_paid` が別イベントとして表に増え、
`Paid × cancel` が偽の穴として出る。

## 語彙を案件から持ち出さない — **実際に起きた失敗**

同じセッションで複数の案件を扱うと、**直前に読んだ案件の語彙が次の案件に漏れます。**

このハーネス自身がその失敗をやりました。実案件（肌解析アプリ）を分析した直後に
架空のサンプル（テイクアウト注文アプリ）を作ったところ、サンプルの論点に
**「診断データの保持期間」**という、注文アプリにはあり得ない語が紛れ込みました。
結果、サンプルを見た人が「なぜ自分の案件に注文と決済の話が入っているのか」と混乱しました。

守ること:

- **グリッドの行を引くときは、その案件の資料に実際に出てくる語だけを使う。**
  「たぶんこう呼ぶだろう」で書かない。資料を開いて、書かれている語を写す
- **論点のタイトルも同じ。** 自分が直前に別案件で使った言い回しを流用しない
- 議事録からの抽出は `quote` の原文照合が守ってくれるが、**グリッドの行には
  その守りが無い。** ここだけは人が見るしかない
- 迷ったら `reqmap doctor` を実行する。「論点があるのに語が1件も当たらない行」は、
  語が案件の実体と合っていない合図

## 観点が出すぎる／出なさすぎるとき

| 症状 | 直すところ |
|---|---|
| 無意味なマスが多い | 行・列の粒度が細かすぎる。統合する |
| 既存の論点と重複する | 第3フィールドの語が足りない。題名に出る語を足す |
| 何も出ない | 行・列が案件の実体と合っていない。設計ドキュメントから引き直す |
| 全部 high で読めない | `reqmap.yml` の `areas` のリスクを見直す。全部 high は無意味 |

グリッドの行・列は**実データ構造と一致させる**。
例: 問診回答が診断データに含まれるなら、独立行にせず診断データの行に畳む。
